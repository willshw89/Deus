### 2. Depth Sorting Mechanism (`Tilemap.prototype._compareChildOrder`)
- **File**: `game/js/rmmz_core.js` (lines 2650–2662)
- **Source**:
  ```javascript
  Tilemap.prototype._sortChildren = function() {
      this.children.sort(this._compareChildOrder.bind(this));
  };

  Tilemap.prototype._compareChildOrder = function(a, b) {
      if (a.z !== b.z) {
          return a.z - b.z;
      } else if (a.y !== b.y) {
          return a.y - b.y;
      } else {
          return a.spriteId - b.spriteId;
      }
  };
  ```
- **Limitation**: Evaluates only integer `z`, screen `y`, and creation `spriteId`. Multi-tile structures, elevated platforms ($Z > 0$), and 2.5D axonometric overhangs require topological or calculated depth keys rather than naive screen $Y$.

### 3. Camera Scrolling and Viewport Clamping (`Game_Map.prototype.setDisplayPos`)
- **File**: `game/js/rmmz_objects.js` (lines 6287–6304)
- **Source**:
  ```javascript
  Game_Map.prototype.setDisplayPos = function(x, y) {
      if (this.isLoopHorizontal()) {
          this._displayX = x.mod(this.width());
          this._parallaxX = x;
      } else {
          const endX = this.width() - this.screenTileX();
          this._displayX = endX < 0 ? endX / 2 : x.clamp(0, endX);
          this._parallaxX = this._displayX;
      }
      // (vertical clamping identical)
  };
  ```
- **Behavior**: Restricts scrolling strictly within `[0, width - screenTileX]`. If map width is smaller than the viewport, centers the map (`endX / 2`).

### 4. World Representation Architecture Decision
- **Question**: Should DEUS treat RPG Maker maps as primary world representation, or host maps with neutral simulation data driving rendering?
- **Evidence**:
  - `game/data/Map001.json` is 50×40 tiles (a minimal editor canvas). A single 256×256 area requires 65,536 tiles per stratum. At 5 vertical strata, a single chunk exceeds 327,000 cells—far exceeding RMMZ's static editor map efficiency.
  - `DEUS_World.js:2368` dynamically generates `$dataMap` in memory from procedural seed data, bypassing disk maps entirely.
- **Architectural Conclusion**: RPG Maker maps must act as **host maps and entry points only**. The authoritative simulation state lives in neutral world data structures (`World.state`, chunk matrices, entity registries).

  Game_Map.prototype.canvasToMapX = function(x) {
      const tileWidth = this.tileWidth();
      const originX = this._displayX * tileWidth;
      const mapX = Math.floor((originX + x) / tileWidth);
      return this.roundX(mapX);

## Area 5: Persistence and Deployment

### 1. Serialization Pipeline (`StorageManager.saveObject`)
- **File**: `game/js/rmmz_managers.js` (lines 549–618)
- **Pipeline**:
  1. `StorageManager.objectToJson(object)` -> `JsonEx.stringify(object)`
  2. `StorageManager.jsonToZip(json)` -> `pako.deflate(json, { to: "string", level: 1 })`
  3. `StorageManager.saveZip(saveName, zip)` -> `saveToLocalFile` (in NW.js) or `saveToForage` (in browser).

### 2. Missing Cycle Handling in JsonEx (`JsonEx._encode`)
- **File**: `game/js/rmmz_core.js` (lines 6458–6475)
- **Source**:
  ```javascript
  JsonEx._encode = function(value, depth) {
      // [Note] The handling code for circular references in certain versions of
      //   MV has been removed because it was too complicated and expensive.
      if (depth >= this.maxDepth) {
          throw new Error("Object too deep");
      }
      // ...
  };
  ```
- **Fatal Risk**: If any object in the save tree contains a cyclic reference, `JsonEx._encode` recurses to depth 100 and throws an unhandled `Error: Object too deep`.
- **Absolute Rule**: PIXI objects, sprites, functions, event listeners, and bidirectional object graphs MUST NOT be included in the save tree. Only normalized IDs and plain data are permitted.

### 3. Save Location (`StorageManager.fileDirectoryPath`)
- **File**: `game/js/rmmz_managers.js` (lines 762–771)
- **Path**:
  `path.join(path.dirname(process.mainModule.filename), "save/")`  
  File names: `file<id>.rmmzsave`, `global.rmmzsave`, `config.rmmzsave`.
- **Safety Mechanism**: Uses atomic rename: creates `file_.rmmzsave`, writes data, unlinks backup, and renames.

### 4. Missing Asset Error Behavior (`ImageManager.throwLoadError`)
- **File**: `game/js/rmmz_managers.js` (lines 988–1006)
- **Behavior**: When a requested bitmap fails to load, `Bitmap.prototype._onError` sets `_loadingState = "error"`. During the next frame, `ImageManager.isReady()` detects `bitmap.isError()` and throws `["LoadError", bitmap.url, retry]`, which terminates scene execution and displays a fatal loading error screen.

## Area 6: Performance and Failure Behavior

### 1. Entity Update Performance (Synthetic Probe)
- **Probe File**: `scratch/synthetic_probe.js`
- **Results**:
  - 100 entities: 0.137 μs/entity/tick
  - 500 entities: 0.015 μs/entity/tick
  - 1,000 entities: 0.018 μs/entity/tick (1.8 ms for 100 ticks)
  - 5,000 entities: 0.018 μs/entity/tick (9.0 ms for 100 ticks)
- **Finding**: Ticking up to 1,000 entities in JavaScript takes < 2 ms CPU time, well within the 16.6 ms frame budget. Above 1,000 entities, update cadences must be staggered across time slices.

### 2. Spatial Query Scaling (Synthetic Probe)
- **Results**:
  - 1,000 objects: Scan 7.36 μs vs Spatial Map 6.85 μs (1.1x speedup)
  - 10,000 objects: Scan 94.24 μs vs Spatial Map 6.16 μs (15.3x speedup)
  - 50,000 objects: Scan 181.25 μs vs Spatial Map 74.34 μs (2.4x speedup)
- **Finding**: Spatial hash grids maintain constant-time localized queries, whereas linear scanning degrades rapidly with object count.

### 3. Save Compression (Synthetic Probe)
- **Results**:
  - Uncompressed JSON: 97,438 bytes (~95 KB)
  - Compressed `.rmmzsave` with pako deflate: 8,628 bytes (~8.4 KB, 91.1% compression ratio)
  - Save serialization latency: 10.6 ms; Load deserialization latency: 7.0 ms.
- **Finding**: Pako deflate level 1 provides massive size reduction with minimal CPU overhead, safely avoiding RMMZ's 50 KB save file warning limit.
