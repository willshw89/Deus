## What Lane K actually measured

The [stress scenario](../../tools/bench_render_layers.js#L522) ran the RMMZ/NW.js engine on a disposable `game/` snapshot at 816 × 624 and 1× zoom. It filled the 17 × 13 visible-cell window across the +2, +1, and ground levels through openings; units walked and fought with melee, ranged, and spell actions. Day and night each ran for 30 seconds in each of two runs, using fixture seed `0x5eed0019`. The source [wraps update, render, and depth operations](../../tools/bench_render_layers.js#L235), counts WebGL draw calls, and records frame intervals. Depth sorting and per-unit simulation/combat logic were in scope. The fixture added 221 units in run 1 and 219 in run 2. The `environment.units` figure is captured [before the fixture is added](../../tools/bench_render_layers.js#L411): it counts the pre-existing loaded world, not simultaneously animated visible sprites.

The rendering technique is the game's regular viewed-level `Sprite_Character` path plus [ordinary `Sprite` objects inside `PIXI.Container` depth planes](../../game/js/plugins/DEUS_Depth.js#L779), with [entity child sorting](../../game/js/plugins/DEUS_Depth.js#L950). The fixture [cycles six existing character sheets](../../tools/bench_render_layers.js#L530); lower planes use [cached `ImageManager.loadCharacter` bitmaps and sprite frames](../../game/js/plugins/DEUS_Depth.js#L591). This allows ordinary engine/PIXI sprite batching where textures and state permit. Sheet reuse is not a custom texture-atlas optimization. The benchmark and depth implementation show no project-specific GPU instancing pipeline or `ParticleContainer` use; [instrumentation mentions instanced WebGL entry points](../../tools/bench_render_layers.js#L225) only to count calls if they occur, not to create such a pipeline.

These are the values in the [raw JSON](../../tasks/WG.00.09b/lane-k/perf/stress_baseline_c2184c94.json), also transcribed in the [report](../../tasks/WG.00.09b/lane-k/REPORT.md#L165). The script [calculates FPS as `1000 / median frame interval`](../../tools/bench_render_layers.js#L327); those FPS values are derived from measured intervals, not an independent GPU frame-rate measurement. The run measured engine update and render submission, not asynchronous GPU completion. It used the `nw.exe` harness, not an RMMZ editor F5 playtest.

The machine metadata says MSI host, 16 logical CPUs, and **AMD Ryzen 7 8845HS with Radeon 780M Graphics**. The latter is the CPU model string, including its integrated GPU. Both runs' WebGL renderer field identifies the **active renderer as NVIDIA GeForce RTX 4060 Laptop GPU through ANGLE/D3D11**; these runs must not be described as Radeon 780M GPU results. Both runs were labeled `quiet` by the benchmark's concurrent-load check. The record does not establish GPU utilization or a separate GPU render-completion time. See the [raw machine and renderer fields](../../tasks/WG.00.09b/lane-k/perf/stress_baseline_c2184c94.json) and [escalation evidence](../../tasks/WG.00.09b/lane-k/escalation.md#L38).

This was a meaningful three-level combat stress, with important visual limits: on the viewed level it used game animation and combat effects; on lower levels `DEUS_Depth` drew walk/stand frames while attacks resolved in simulation, but did not draw lower-level attack frames, hitsplats, action bars, or RMMZ animations. The bench supplied solid-colour placeholder projectile and lower-level impact sprites where game assets/paths were missing. Those omissions and the 816 × 624 window prevent extrapolating to a million fully animated sprites, all combat visuals, or 1080p. See the [effect-path and placeholder declarations](../../tools/bench_render_layers.js#L525).
