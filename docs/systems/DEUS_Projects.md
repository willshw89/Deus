# DEUS_Projects

Settlement projects: the colony-level planner that measures what the settlement lacks (shelter, food, sheltered beds, storage), picks the one need worth acting on (the settlement brain, DEUS-TSK-FABLE-06), opens a project from that need's blueprint, reserves the project's cells, and posts ordinary open `UF_Jobs` jobs for the current phase. The planner never orders a unit around: its jobs are open designations, taken by whoever takes open jobs: the founders through `UF_Colonists`' decision loop (`decide`, restored 2026-09-23 under DEUS-TSK-FABLE-03; it takes project jobs before the society plan), or the player through overseer orders and `UF.Jobs.assign`.

**Owner:** Claude Code (Fable) · **File:** `game/js/plugins/DEUS_Projects.js` · **Load order:** after `DEUS_Jobs` and `DEUS_Colonists`; before `DEUS_Test`. Delivered 2026-09-22 under DEUS-TSK-FABLE-02; the settlement brain 2026-09-23 under DEUS-TSK-FABLE-06. Registered in `game/js/plugins.js` after `DEUS_Colonists` (2026-09-23).

## 1. Purpose

One source of truth for settlement-level deficits and blueprint construction. `UF_Colonists` keeps its society plan (the step list around the hearth: hearth, larder, knives, clothes, the 7×7 town shelter, door, chest, beds, workshops). This plugin adds the deficit-driven layer beside it: it reads the plan's cells and the camp ring as reserved ground, so the two never compete for a cell, and it counts whatever the plan builds (a door set into walls, beds, stockpiles) as supply, so a plan-built shelter closes the deficit without a project. While this plugin is enabled, `UF_Colonists` skips the plan's shelter, door, beds and chest steps (DEUS-TSK-FABLE-03), so those come from projects.

Timing is explicit: every timer carries `domain: "action"` and counts map updates (the same count `UF.Time.ticks()` keeps, so speed-up and pause carry over). Nothing scans the world per frame: the per-update cost is one tick comparison plus a look at the (usually zero or one) active projects' recheck timers.

## 2. Public API (`UF.Projects`)

Configuration comes from `catalog.colony.projects` when present, else the defaults below (`Projects.config()` returns the merged object).

| Key | Default | Meaning |
|---|---:|---|
| `cadenceTicks` | 3000 | map updates between full cycles (~50 s at 60 updates/s) |
| `startDelayTicks` | 120 | first cycle this long after the colony exists or a save loads |
| `perShelter`, `perStockpile` | 8, 8 | colonists per communal shelter / stockpile |
| `scanRadius` | 24 | cells around the hearth counted as the settlement |
| `siteSearchRadius` | 40 | Chebyshev distance searched for a footprint |
| `margin` | 1 | free ring kept around a footprint |
| `materialRadius` | 40 | how far a haul or harvest may reach from the site |
| `maxOpenJobs` | 12 | posted jobs alive at once per project |
| `harvestPerMaterial` | 2 | harvest jobs alive at once per missing material |
| `jobPriority` | 0 | `UF_Jobs` priority of posted jobs (0 = like any designation) |
| `recheckTicks` | 60 | a build square somebody stands on is looked at again after this |
| `retryTicks` | 9000 | a cell whose jobs failed three times waits this long |
| `staleTicks` | 600 | an untaken haul, harvest or build job every colonist found undoable for this long (one game hour) is withdrawn |
| `giveUpTicks` | 43200 | a project with nothing workable for this long (three days) is cancelled and its kind cooled; 0 = never |
| `targetReserveDays` | 3 | food: colonist-days of nutrition the settlement keeps within reach |
| `slotsPerColonist` | 1 | storage: physical slots each colonist needs (DEUS-TSK-GEMINI-07: one stack a cell) |
| `slotsPerStockpileCell` | 1 | storage: what one stockpile cell counts as (a chest counts its `maxSlots`) |
| `forageJobs` | 4 | food: gather jobs a food cache keeps alive at once |
| `reserveMarginDays` | 0.5 | food: a cache forages this far past the target, so one meal does not reopen a cache at once |
| `kindCooldownTicks` | 6000 | a kind that could not open, or whose forage found nothing, waits this long |
| `severity` | shelter 3, food 2, foodCritical 4, bed 1.5, storage 1 | the brain's weight per deficit |
| `survivalBonus` | foodCritical 5, shelter 2 | added to the utility of a critical food or an unmet shelter deficit |
| `blueprints` | the four below | blueprint records, overridable per id (`null` switches one off) |

Blueprints (`kind` `footprint`: a square site chosen outside the camp; `kind` `task`: cells chosen inside settlement space, or none at all):
- `communal_shelter` (deficit `shelter`, footprint `size 5`): `wall wall_wood`, `door door_wood` (south middle, `(origin.x+2, origin.y+4)`), `hearth campfire` (centre), `bed floor_straw` (the 8 interior cells); phases `site → walls → hearth → beds`; capacity `{ shelter: 1, bed: 8 }`. Geometry is derived from `size`, so a catalog blueprint with another size gets the matching perimeter, centre and interior.
- `communal_stockpile` (deficit `storage`, footprint `size 3`): `fill stockpile` with `stores ["wood","stone","metal","material"]`; phases `site → stockpile`; capacity `{ storage: 72 }` (9 cells × `slotsPerStockpileCell`).
- `bedding_expansion` (deficit `bed`, task): `bed floor_straw` on up to 16 free sheltered cells (`sheltered()`, nearest the hearth first); one phase `beds`; capacity `{ bed: cells }`.
- `food_cache` (deficit `food`, task): phase `larder` builds a `stockpile` with `stores ["food"]` at the existing larder (the first `colony.stockpiles` entry storing food) or a chosen 1×1 site; phase `forage` hauls loose food into it and gathers wild food until the reserve holds; capacity `{ food: the deficit at opening }`.

- `evaluateDeficits(area?)` → `{ area, site, radius, population, shelter, food, bed, storage, evaluatedAt: { domain, tick } }` or `null` (no colony); each row is `{ needed, current, deficit, unit }`. `area` defaults to the colony's; another settlement's area resolves through `colony.settlements`. Population = units with `data.kind === "colonist"` in the area. One `Objects.findIn` scan of `building`-tagged objects within `scanRadius` of the hearth, one `Items.find` of `food`-tagged stacks in the same radius, and the containers `UF.Containers.all` lists there:
  - `shelter`: a `door` tag with at least two `wall`-tagged 4-neighbours; needed `ceil(population / perShelter)`.
  - `food` (unit `colonist-days`): nutrition in pounds of the SRD daily need, `food.nutrition × count` of each stack (never its weight), in larders (`larderLb`), containers (`containerLb`), on the ground (`groundLb`) and in the packs of the settlement's living colonists (`carriedLb`), divided by the population; needed `targetReserveDays`; also `lb`, `deficitLb` and `critical` (under one colonist-day). Two sums answer two questions (DEUS-TSK-FABLE-07): `totalAccessibleNutrition` (all four; "can we survive?", the one the deficit uses, since a colonist eats from its own pack first) and `communalStoredNutrition` (larders and containers only, also `storedLb` and `communalDays`; "what is deposited?", for logistics). Every stack is counted once wherever it lies (a pack and the pouch in it, a container and a cell), so a deposit moves food without adding any. The dead are neither population nor holders; their packs follow the corpse.
  - `bed`: `bed`-tagged objects on sheltered cells only (`unsheltered` counts the rest); needed `population`.
  - `storage` (unit `slots`): container `maxSlots` (`containerSlots`) plus passable, non-container `stockpile`-tagged cells (`stockpileCells`) × `slotsPerStockpileCell`; needed `population × slotsPerColonist`.
- `explain(area?)` → "Shelter 0/1 (needs 1 more) · Food 1/3 days (needs 2 more) · Beds 3/8 (needs 5 more) · Storage 8/64 (needs 56 more) slots · 8 colonists within 24 of (128,128); next: communal_shelter (utility 5.0)". For `UF_Look` / `UF_Sheet`.
- `brain()` → `{ deficits, candidates: [{ kind, deficit, total, needed, unit, inFlightCapacity, inFlightProjects, unmet, fraction, severity, bonus, utility, cooled, eligible }], chosen }` sorted by utility. For each blueprint: `unmet = max(0, deficit − Σ capacity[deficit] of active projects)` (so a need one project already covers never opens another: a shelter in flight covers 8 beds, no bedding opens beside it); `utility = severity × min(1, unmet / needed) + bonus − activeOfKind × 10` when `unmet > 0`, else `−∞`; `bonus` is `survivalBonus.foodCritical` for food under one colonist-day (with `severity.foodCritical`) plus `survivalBonus.shelter` for an unmet shelter; `eligible` needs `unmet > 0`, no cooldown on the kind and a positive utility (the active-project penalty keeps a second project of a kind from opening beside one in flight: a food cache forages until the reserve holds whatever the deficit grew to, the next shelter waits for the first); `chosen` is the first eligible candidate.
- `deficits` → `["shelter", "food", "bed", "storage"]`. `sheltered()` → the sheltered cells: the camp's interior inside its ring (`colony.radius − 1` around the hearth) and the bed cells of every finished communal shelter.
- `tick()` → runs a full cycle now: `{ deficits, brain, opened: [ids], advanced: [{ id, phase, total, done, todo, blocked, posted, waiting, standers, reserveDays? }] }`. A cycle opens at most one project, the brain's `chosen` kind (a kind that returns no project is cooled for `kindCooldownTicks`), then advances every active project.
- `open(kind, { origin?, count?, deficits?, utility? })` → the project or `null` (no colony, unknown blueprint, no valid footprint, no free sheltered cell). `origin` fixes a footprint project's site; `count` bounds a bedding project's beds (default the bed deficit, at most 16); `deficits` is the evaluation to size the capacity from.
- `advance(id)` → that project's advance summary now (or `null`).
- `cancel(id, reason?)` → bool; cancels the project's live jobs through `UF.Jobs.cancel`.
- `list(filter?)`, `get(id)`, `active()`, `state()` (the saved record below), `blueprint(kind)`, `blueprints()`.
- `reservedAt(area, x, y)` → the id of the active project whose footprint holds the cell, else `null`. Other planners (households, roads, plazas) should consult it before claiming ground.
- `footprint(project)` → the project's cells (the square of a footprint project, the chosen cells of a task project); `cells(project, phase?)` → `[{ x, y, object, state }]` with `state` `done | clear | build | blocked` for the phase (default: the current one).
- `describe(idOrProject)` → "Communal shelter #1 at (140,120)-(144,124): phase 2/4 walls, 9/16 cells, 3 jobs open, 2 taken, waiting for log".
- `setEnabled(on)`, `isEnabled()`; `timers` (the tagged cadence and start delay); `_internal` (pure helpers for tests: `chooseSite`, `siteValid`, `reservedCellSet`, `cellStatus`, `canFullyClear`, `clearAction`, `relativeCells`, `harvestSources`, `foodSources`, `shelteredCells`, `beddingCells`, `larderCell`, `capacityFor`, `brain`, `coolKind`, `onMapUpdate`, `onLoaded`, `now`).

- `structures()` → the finished footprint projects and their ground, `[{ id, kind, origin, size, cells }]`, for other planners to keep clear of (DEUS-TSK-FABLE-13).

### Hearths, homes and phases (DEUS-TSK-FABLE-16, 2026-09-24)

Owner directives 2026-09-24: the communal shelter was a fire trap (its campfire hearth sat between four straw beds, and the catalog lets a campfire light a flammable neighbour at 0.0005 a beat: about a 38% chance a day of a bed catching on screen); and the settlement stopped after the first communal shelter because eight beds for eight people read as "nothing to build".

**Config** (catalog `colony.projects` overrides): `hearthClearance` 1 (no bed or other furnishing within this many orthogonal steps of a blueprint's hearth), `cottageBeds` 3, `villageFoodDays` 3, `townPopulation` 16, `severity.housing` 2.5, `phaseBonus.housing` 1.

**Blueprints.** A blueprint's `hearth` names a contained fire source: `"hearth"` resolves through `hearthId(bp)` to the first of `hearth`, `kitchen_hearth`, `campfire` the catalog defines (today the catalog has no `hearth` object, so the shelter builds the cooking hearth, `kitchen_hearth`: 4 stone and a log, which `UF_Fire` treats as contained by type; a campfire is the last resort and the finished building marks it contained). `relativeCells(bp, bedCount)` puts the hearth at `(mid, mid)`, keeps its orthogonal neighbours within `hearthClearance` free of everything (the cell between the door and the hearth is the walkway; nothing flammable touches the fire), and lays beds on the other interior cells, `bedCount` of them at most, with a chest on the last cell when the blueprint has one.
- `communal_shelter` is now **6×6** (20 wall and door cells, the door at `(origin.x+3, origin.y+5)`, the hearth at `(+3, +3)`, 4 clearance cells, **11 beds**; capacity `{ shelter: 1, bed: 11 }`), so eight founders and their first arrivals sleep under one roof.
- `household_cottage` (deficit `housing`, footprint size 5): `wall_wood`, `door_wood`, `hearth`, `floor_straw` on the corners (as many as the household's members, up to `cottageBeds`) and a `chest_wood` on the last corner; phases `site → walls → hearth → beds → chest`; capacity `{ housing: 1, bed: n }`. There is exactly one dwelling blueprint (one source of truth per concept, Rule 14); variants belong in the catalog override.
- `bedding_expansion` never lays a bed orthogonally adjacent to a fire source (`nextToFire`); `shelteredCells` includes the bed cells of every finished blueprint with a hearth and beds (shelters and cottages).
- A hearth cell already holding a fire-tagged object (a campfire an older blueprint built) counts as done; when a building finishes, `containHearth` marks its hearth cell contained in `UF.Fire` (`setContained(area, x, y, true, "project:<id>")`), and once after a load `sweepContainment` does the same for every finished building of an older save.

**Emergency shelter vs domestic housing.** `evaluateDeficits` keeps the rows above and adds `shelter.emergency = { needed: population, current: sheltered beds, deficit }` ("can everybody survive tonight?") and `housing = { needed: eligible households, current: housed ones, deficit, households: [{ id, size, adults, eligible, housed, homeBuildingId, source }], domestic: { needed, current, deficit } }` ("does every household have an adequate permanent home of its own?"). The communal shelter houses nobody. Households (`householdsOf`, also `Projects.households()`): `UF.Households.all()` records of the settlement's level and faction when that plugin is loaded (members through `UF.Households.members`), and, for colonists no record covers, groups from their own data: `householdId`, else a partner pair (each other's `partnerId`, both alive), else a child (under 15) with a living parent, else alone; keys `hh:<id>`, `pair:<lowest unit id>`, `unit:<id>`. Eligible: at least one member of working age (15). Housed: a finished `household_cottage` holds the household (`Households.homeBuildingId`, else `state.housing[key].buildingId`) whose `bedCount` covers its members up to `cottageBeds`.

**Phase** (`phaseOf(d)`, `Projects.phase()`, `d.phase`, `brain().phase`): `camp` while no communal shelter stands, anyone lacks a sheltered bed, the food reserve is under `villageFoodDays` or storage is short; `village` once those hold; `town` at `townPopulation` or more. The brain gates the `housing` candidate on the phase (`phaseOk`; camp: utility −∞, never eligible) and adds `phaseBonus.housing` from the village on, so a cottage outranks more beds and storage but never an unmet shelter, an emergency bed deficit or critical food.

**Opening and finishing a cottage.** `open("household_cottage")` picks the first eligible unhoused household (by id) no active cottage is already for, records `p.household = { id, source, members, size }` and `p.bedCount`; one cottage at a time (the active-kind penalty). When it finishes: `containHearth(p)`, then `moveIn(p)`: `UF.Households.assignHome(id, spec)` when the household came from that plugin (its `home` record gets the cottage's walls, door, beds, hearth, chest and entrance; `homeBuildingId` = the project id; `isMovedIn`), `state.housing[id] = { buildingId, members, at }` in every case, then each living member claims one cottage bed through `UF.Colonists.claimBedAt` (the communal bed it held is free for the next arrival; `UF_Colonists`' bed allocation runs at its next sweep). `p.movedIn = { household, members, claimed, at }`; emits `projects:movedIn(project, householdId, claimedIds)`.

- `phase()`, `phases` (`["camp", "village", "town"]`), `households()`, `hearthId(bp)`, `hearthCellOf(project)`; `deficits` → `["shelter", "food", "bed", "storage", "housing"]`; `explain()` starts with the phase and ends with "Homes 1/4".

### Fire at a project (DEUS-TSK-FABLE-18, 2026-09-24)

Owner directive 2026-09-24: colonists must abandon doomed construction, not resume dangerous jobs blindly, and not rebuild the same bad structure in the same bad way. Only `UF_Fire`'s spreading fire counts here (`isBurning`); a hearth or campfire standing in its place is not a fire at the site.

**Config**: `fireCalmTicks` 300 (half a game hour), `fireClearance` 3, `burnLimit` 2, `burnIncidentTicks` 14400 (a game day).

- **Doomed construction** (`fireHold(p)`, run by `advance` right after `reconcile`). While a square on or beside the project's cells burns (`siteBurning(p)`: the footprint plus a one-square ring; a task project's cells plus their neighbours), every job the project posted, open or taken, is cancelled with `fire: the site is burning` (`withdrawAll`), nothing is posted and the phase does not step. `p.fire = { since, calmSince, withdrawn }`; the project is looked at again every `recheckTicks`. Once the site has had no burning square for `fireCalmTicks`, `p.fire` is cleared and the work resumes from the world as it is (a burned wall is simply a `build` cell again). `fire:` reasons are never cell faults, so no square is blamed for a fire. `fire:ignited` on or beside an active project's cells marks it for an advance on the next update, so the hold starts at once rather than at the next cycle.
- **Burned sites** (`noteBurn`). A square inside a footprint project's square (active or finished) catching fire adds its fire id to `colony.projects.burnedSites`: `{ kind, origin, size, count, fires: [fireId…], last: { fireId, project, kind, sourceType, sourceCell, at } }`. `count` is the number of incidents: fires within `burnIncidentTicks` of the last one noted there are the same incident (two walls lit at once are one burn). The record outlives the project.
- **Siting** (`siteHazards(c, n, cfg)`, gathered once per `chooseSite`; `siteValid(area, ox, oy, n, margin, reserved, hazards)`). A new footprint keeps more than `fireClearance` squares from any square burning now and from any fire source no hearth contains (`UF.Fire.sourceInfoAt(...).contained` false: an open campfire), and never overlaps (with its margin) a site whose `count` reached `burnLimit`. One burn does not rule a site out (a wildfire can pass anywhere); a second does.

`UF_Jobs` covers the individual worker (`docs/systems/UF_Jobs.md`: a job at a burning site is not taken and a taken one fails `fire at the work site`), and `UF_Colonists` reroutes a colonist whose path a new fire crossed (`docs/systems/DEUS_Colonists.md`).

**Growing past the first shelter** (DEUS-TSK-FABLE-13). Nothing special opens a second dwelling: the deficit rows scale (`shelter` needs `ceil(population / perShelter)`, `bed` needs `population`, `storage` needs `population × slotsPerColonist`), so a colony of nine to sixteen reads a second shelter as unmet and the brain opens another `communal_shelter`, then another `communal_stockpile` when the slots run short; a shelter in flight covers its eight beds, so no bedding project opens beside it. `chooseSite` keeps every new footprint apart from what stands: `siteValid` refuses any footprint whose square, or `margin` ring round it, holds a constructed object (walls, doors, beds, stockpiles, hearths) or a square in `reservedCellSet` (the camp ring and its plan, registered stockpiles, active projects with their margin), so a second shelter never covers or touches the first, the camp or a stockpile; clearable growth (trees, shrubs, rock) on the parcel is felled or quarried in the `site` phase. Nothing is ever taken out of a standing building: `harvestSources` indexes only unconstructed types (a wall's own `chop` yield is never a source), and `sources` never lifts a stack off a square an active project has reserved. **Parcel tidy**: once the site phase has cleared the parcel, `tidyParcel` posts hauls (`params.tidy`) for the loose material the clearing left on it (logs, stone, straw) to a registered stockpile cell with room (`stockpileCellFor`: `UF.Stockpiles.findDestination` when loaded, else the nearest registered cell whose `stores` take the item's kind and that holds nothing but the same kind under its stack limit, counting what is already on its way there), and the phase waits for them; a stack is offered at most `TIDY_TRIES` 3 times (a carrier may lift only part of it), and with no stockpile room the material stays on the parcel and the build uses it there.

**Choosing a footprint** (`chooseSite`): rings of Chebyshev distance 1… `siteSearchRadius` around the hearth; candidates in a ring are ordered by `World.hash32(seed, cx, cy, salt)` (no `Math.random`); the first valid origin wins. Valid: every cell of the footprint plus `margin` lies at least one cell inside the area, is not water (`UF.Jobs.isWaterAt`), has walkable ground (`World.walkable` with `ground: true`), is not reserved (the camp ring `colony.radius + 1` around the hearth, every `build` step's cells of `colony.plan`, `colony.stockpiles`, other active projects' footprints plus margin), and holds no constructed object; a natural object is fine when it is passable or has a harvest action `UF_Jobs` knows (`chop`, `gather`, `pick`, `quarry`, `mine`, `dismantle`).

**Advancing a project** (work recovery, DEUS-TSK-FABLE-08/09): stale jobs are withdrawn first: an open, untaken haul whose item is gone, carried, boxed or moved (a colonist ate or hauled it); a harvest whose plant no longer offers the action (somebody else picked it); a build whose square is already built or blocked by somebody else, or whose materials are gone from the square (they are hauled again instead of a build job claiming the square forever); or any haul, harvest or build that every colonist who looked at it found undoable (`UF_Jobs`' dry run leaves `job.reason`) for `staleTicks`. Each is cancelled with reason `stale: …`; a target withdrawn for its dry-run reason (read before the cancel overwrites it) waits `retryTicks` before it is chosen again, so an unreachable tree or square is not posted every hour. Left alone, such jobs filled the slots and phases stalled: foraging stopped while food stood regrown, a wall waited for logs a build job already claimed. Then finished jobs are dropped from the maps. A failure counts against its cell only when the cell is at fault (`can't reach …`, `nowhere to take it`, `the square is taken`; three such pause the cell for `retryTicks`); a vanished, carried or moved item, a picked plant, missing materials, a departed worker, a survival interruption (`survival: …`) or a stale withdrawal never count: the job is posted again from the world at the next advance, and the reservations `UF_Jobs` released go to whoever takes it. A haul `UF_Jobs` finished without a result (a full larder or container refused the delivery) marks the destination `refused` for `retryTicks`: the food cache hauls to another registered larder meanwhile and offers the first again when the refusal expires; a build square that refuses is reported and waits.

**Paused, not frozen.** When nothing of a phase is workable (every remaining cell blocked, materials nothing within reach yields (`no straw within reach`), cells waiting to retry, deliveries refused) and no job of the project is alive, the project records `blockedSince`, reports the reason in `describe()` ("…; paused since tick 854"), looks again every ten `recheckTicks`, and emits `projects:paused` (`projects:resumed` when work is possible again). After `giveUpTicks` of that (0 = never) it cancels itself with `gave up: <reason>` and cools its kind, so its ground and the deficit are free for a fresh attempt; no job or reservation of it remains. A paused project posts nothing, so the colonists' dispatch is never held by it.

**Idle strolls yield to posted work.** For every project job posted and still untaken, the nearest colonist of the faction on a low-priority idle job (`UF_Colonists`' stroll, exploration, inspection, contemplation, hearth or social idling; never a player's order, `params.ordered`) is taken off it with reason `work: project posted`; `UF_Jobs`' cancel releases its reservations and `UF_Colonists` decides again at once, project work first. Deterministic: nearest first, then unit id. For each cell of the phase, `cellStatus` reads the world: `done` (holds the target, or nothing to clear in the site phase), `clear` (a natural object with a harvest action that `canFullyClear`: one job of that action, so a tree is chopped and a shrub gathered, and a stump chopped after), `build` (the target object is missing), `blocked` (another building, or an object no job clears; reported, never removed). `canFullyClear(t)` follows the harvest's `becomes` chain: the remainder must be passable or clearable in turn, so an oak (stump, choppable) clears and a berry bush (bare bush, no action) does not; `siteValid` uses the same query, so such a footprint is never chosen (DEUS-TSK-FABLE-04). A `build` cell gets a `build` job once every `build.items` count lies on it (with `UF_Jobs`' substitutes: `log` for `wood`, `fiber` for `straw`, `rocks_small` for `stone`); otherwise `haul` jobs, one per source stack, from the nearest unclaimed ground stacks within `materialRadius` that do not lie on a reserved footprint. A haul asks for exactly what the cell still needs (`params.count`, splitting a bigger stack on its cell first); how much of it one carrier lifts is `UF_Jobs`' legal-lift rule (`docs/systems/UF_Jobs.md`), and what stays behind is hauled next. When no stack covers the need, up to `harvestPerMaterial` harvest jobs go to the nearest catalog objects whose action yields the material (an oak for logs, a shrub for fiber, loose stones for stone), outside every reserved footprint. A square somebody stands on is skipped and rechecked after `recheckTicks`. When no cell is `todo` or `blocked`, the phase steps and `advance` runs again at once for the new phase (bounded by the number of phases), so its first jobs are posted in the same update rather than at the next cadence cycle; after the last phase the project is `done`. A stockpile cell's build job carries `params.stores` (the blueprint's list), which `UF_Colonists` registers in `colony.stockpiles` on completion.

A `food_cache`'s `forage` phase has no cells. Each advance re-evaluates the deficits and is complete when the reserve reaches the target plus `reserveMarginDays`; otherwise it posts `haul` jobs for loose `food` stacks within `materialRadius` (not in a larder or container, not reserved) to the larder, and keeps up to `forageJobs` gather jobs alive on the nearest catalog objects whose harvest yields a `food` item (`foodSources`: berry bushes, fruit trees, cactus, glow caps, cave mushrooms) outside every reserved cell. A cycle that posts nothing while no job is open counts as blocked (`no wild food within reach` or `wild food is spoken for`); three in a row cancel the project and cool its kind for `kindCooldownTicks`.

Posted jobs are open (`owner null`) with `params.project` (the id) and `params.phase`; hauls also carry `params.material`. The maps `jobs` (cell → job id), `hauls` (item id → `{ job, cell, type, count }`) and `harvests` (cell → `{ job, material }`) keep one live job per cell and per item. Once a colonist takes a job, `UF_Jobs`' reservation manager reserves the target cell and the item for that unit, as for any job.

## 3. Events (`UF.Events`)

- Emits `projects:evaluated(deficits, brain)` (each cycle), `projects:opened(project)`, `projects:sited(project)`, `projects:jobPosted(project, job)`, `projects:phase(project)`, `projects:paused(project)`, `projects:resumed(project)`, `projects:done(project)`, `projects:movedIn(project, householdId, claimedUnitIds)` (DEUS-TSK-FABLE-16), `projects:cancelled(project, reason)`, `projects:fire(project)` (its site started burning; work stopped), `projects:fireOut(project)` (calm for `fireCalmTicks`; work resumes), `projects:burned(project, burnedSiteRecord)` (a square of its footprint caught fire) (DEUS-TSK-FABLE-18).
- Listens: `jobs:done`, `jobs:failed` (a job with `params.project` marks that project for an advance on the next map update); `fire:ignited` (a project on or beside the square is advanced on the next update; a footprint square records the burn).

## 4. Save data

`UF.World.state.colony.projects = { version: 1, nextId, list: [project], cooldowns?: { kind: tick }, housing?: { householdKey: { buildingId, members: [unitIds], at: { domain, tick } } }, burnedSites?: [{ kind, origin: { area, x, y, z }, size, count, fires: [fireId], last: { fireId, project, kind, sourceType, sourceCell, at: { domain, tick } } }] }` (inside the colony record, so it rides in `contents.ufWorld`). A project on hold for fire carries `fire: { since, calmSince, withdrawn } | null` (DEUS-TSK-FABLE-18). A project may also carry `household: { id, source, members, size } | null`, `bedCount: n | null` and `movedIn: { household, members, claimed, at } | undefined` (DEUS-TSK-FABLE-16).

`project = { id, kind, deficit, state: "active" | "done" | "cancelled", phase, origin: { area: { x, y }, x, y, z }, size (0 for a task project), margin, phases: [{ name, task, cells: [{ x, y, object, stores }] }] | null (footprint projects derive their cells from the blueprint), larder: { x, y } | null, capacity: { deficit: amount }, utility, created: { domain: "action", tick }, sited: {…}, finished: {…} | null, jobs: { "x,y": jobId }, hauls: { itemId: { job, cell, type, count } }, harvests: { "x,y": { job, material } }, failed: { "x,y": { count, reason, retryAt } }, blocked: { cell, reason, since } | null, blockedCycles, blockedSince: { domain: "action", tick } | null, refused: { "x,y": { count, since: { domain, tick }, until: { domain, tick } } }, recheck: { domain, tick } | null, reason, log: [{ tick, text }] }`. Posted jobs carry `params.postedAt` (the action tick they were posted). Everything is JSON-safe (ids only, no object references); the harness checks a JSON round trip is identical and that the restored record is usable. Runtime caches (`nextRunAt`, the dirty set, the yield index) are rebuilt after `DataManager.extractSaveContents`.
