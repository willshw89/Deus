## How the checker works

**Inputs** (defaults; each can be overridden on the command line):
- `docs/worldgen/DEUS_WORLD_STATE_REGISTRY.md`: the §2 JSON schema supplies the enums, the required fields and their types. Every table with a "State ID" column supplies rows. A line that looks like a state row but lies outside such a table (no leading `|`, after a blank line or an HTML comment, or indented 4+ spaces) is refused with exit 2, so a row cannot be skipped silently. Parse errors name `file:line`.
- `art/catalogue/catalogue.json`: sheets, entries and slots, plus the `geometry.json` it references, for tilePx and atlasMaxPx.
- The template slot map: generated by `tools/art/make_blank_templates.js` into a fresh temp folder, which is deleted afterwards. The folder is created under the OS temp folder, or under `--work-dir` if given; the tests use a private work folder. `--templates <dir>` reads existing sidecars instead.
- `game/data/UF_WorldCatalog.json`: the same id lists the catalogue ingests. The report shows they equal the catalogue's `sourceIdIndex.catalog` (250 ids, "EQUAL").
- `art/APPROVALS.md`: the SHA-256 ledger section, parsed with Lane U's `parseLedger`.
- Lane U placement outputs: the files given with `--placements`, or `--placements none`. Without the option, every tracked `placement_report.json` under `art/` (`git ls-files`); untracked scratch output never counts.
- `tools/wsr/scope.json`, `tools/wsr/visual_state_map.json` and `tools/wsr/known_gaps.json`.

**Rules and codes** are listed in full in the tool header (`tools/verify_world_state_registry.js`, "Rules and finding codes"). In summary:
- **WSR-01**: one system per state, and the system must be in the enum.
- **WSR-02**: art-required states (VISUAL_REQUIRED and VFX_REQUIRED, from `scope.json`) have a visual state id and a family; SIMULATION_ONLY states have neither. Composed rows are EXEMPT only when both cells are composed and the system is in `composedExemptSystems` (LANDMARKS_HISTORY).
- **WSR-03**: every visualStateId, of any visual class, resolves to a catalogue entry that owns a slot, and that slot is confirmed in the template output with the same sheet and rect. Two more legs are checked. The WorldCatalog leg is the spec's wording. The family leg requires that every family a row names exists in the catalogue.
- **WSR-04**: every slot's class is declared in `scope.json`, checked per slot. NATURAL_WORLD slots trace to a state. A NON_WORLD_STATE slot's entry must cite at least one real source id of its source class. Real means non-empty, listed in the catalogue's `sourceIdIndex` for that kind, and, for catalog ids, present in the WorldCatalog.
- **WSR-05**: every state has a performanceClass from the enum.
- **WSR-SCHEMA**: the seed table has a column for every required field. Required string cells are not empty. Enums, booleans, id format and transitions are valid.
- **MANIFEST-TEMPLATE**: checks that the catalogue and the template slot map agree in both directions on sheet ids, sheet geometry, slot ids, rects and owning entries. Slots lie inside their sheet. ATLAS sheets use the geometry tilePx grid and stay within atlasMaxPx. Every generator refusal is a gap.
- **PLACED-IN-SLOT**: every ledger id is a catalogue entry or slot. A placed region that names a slot must be inside that slot, and the slot must exist and belong to the placed entry; an unknown slot id is never matched against some other slot. A region that names no slot must lie inside some slot on its sheet.

**Resolution** of a `visualStateId` v, documented in the tool header:
- ID: an entry id equals v, or the entry id's TYPE field equals v upper-cased with every character outside [A-Z0-9] turned into `-`.
- SOURCE: the bare source id equals v (catalog list prefix and `SEG-nn:` removed; AR and addendum ids never match).
- MAP: an ACCEPTED map row points at the entry.
- Only entries whose class may display a world state count (NATURAL_WORLD classes, and source classes with `mayDisplayWorldState: true`). An item icon, a person, a creature or a face that shares the id is listed as a rejected match.
- A derived variant uses its base's slot.

The brief also lists "family" as a way to resolve. I did not use family as a resolution method, because the catalogue's `family` field is structural (SOURCE plus the addendum families). "Any entry of family F" would therefore match any member, which is too weak. The family is checked as its own leg instead (`FAMILY_NOT_IN_CATALOGUE`).

**Template slot map when the generator refuses.** On main the generator refuses the catalogue (X-E2), so the checker handles it in steps:
1. It records every refusal as a gap. Each refusal is attributed to a slot, a sheet or the whole catalogue by the id that starts the generator's message.
2. It runs the generator again on a single-file copy of the catalogue that holds only the sheets it did not refuse, and their slotted entries.
3. It repeats until a run succeeds. It stops early on a catalogue-level refusal, or when a run refuses no new sheet.

The test `gen_split_run_keeps_slots` shows that this split changes nothing for the sheets that are kept: slots and template PNG sha256 are identical to the whole-catalogue run on Lane T's fixture.

**Gate:** the key is `(rule, code, id, value)`. The value is the offending value: a system name, a visual state id, the entry owning a slot, or a rect. A gap whose value changes is therefore a new gap, plus a stale baseline entry; it cannot hide under the old entry.
- Default mode exits 1 on a VIOLATION or GAP that is not in the baseline, and on a baseline entry that no longer occurs. EXEMPT findings never gate, and a baseline entry for one counts as stale.
- `--strict` ignores the baseline.
- `--check` compares a fresh in-memory report with the committed one, with CRLF folded to LF.
- Reports have no timestamps and no absolute paths, and arrays are sorted.
- Exit codes: 0 for OK, 1 for a gate failure or a report difference, 2 for a usage error or bad input.

## Disagreements between the registry spec and what exists

None of these is resolved here. Each one is either baselined with a reason or recorded as a parameter.

- **D1. WG.30 atlas vs the catalogue sheets.** WSR-03 (`docs/worldgen/DEUS_WORLD_STATE_REGISTRY.md:218`) asks for "a valid atlas coordinate in `WG.30`". WG.30.01 (`docs/worldgen/DEUS_WORLDGEN_WBS.md:150`, PLANNED) has no deliverable. As the brief instructs, the checker uses the catalogue sheets and slots as the atlas of record, and confirms them in the template output. The report states this under Parameters. WG.30.01 also plans "A1 (water/anim/depth 1..5) … B–E (props/scatter)", RMMZ-style sheets, while the catalogue packs `ATLAS_<band>_<biome>_<type>_nn` sheets.
- **D2. UF_WorldCatalog "active entry" vs the catalogue.** WSR-03 (registry:218) asks that every `visualStateId` "match an active entry in `game/data/UF_WorldCatalog.json`". The WorldCatalog lists runtime content (objects, items, wildlife, people, ground kinds, water, faces, skins, underground grounds; 250 ids) and has no registry visual state: 0 of 40. It also has no "active" flag on entries. The checker keeps this leg (`NOT_IN_WORLD_CATALOG`, 40 baselined), so the spec rule is not dropped silently.
- **D3. Snow and ice states vs the biome registry.** Four states name forbidden biomes: STATE_SNOW_LIGHT_DUSTING, STATE_SNOW_DEEP_STRATUM, STATE_SNOW_SLUSH_THAW (SNOW) and STATE_WATER_FROZEN_ICE (FROZEN, ICE) (registry:162-165). `game/data/DEUS_BiomeRegistry.json:16-22` forbids FROZEN, SNOW, GLACIER, ICE and TUNDRA_SNOW. The catalogue already records the same conflict as Q-SNOW (`art/catalogue/conflicts.md:127`). The report lists the four states under "forbidden biome", and their baseline reasons cite X-Q6.
- **D4. 1-ft and 5-strata assumptions vs DEC-013 geometry.** The registry measures snow in feet (`0.1..0.5 ft`, `1.0..3.0 ft`, registry:162-163) and fluid in depth bands (`depth 1..3`, `depth 3..5`, registry:133 and 135). `docs/worldgen/DEUS_NATURAL_WORLD_SYSTEMS.md` reads those bands as 1-ft strata: ":57 water … occupies physical 1-ft strata cells", ":106 deep snowpack (1-ft to 3-ft strata)", ":317 Depth 1 (1 ft)". It also says ":14 5 macro-Z levels, 5 physical strata". The DEC-013 geometry the catalogue uses is `stratumFt 2`, `layerFt 10`, `layerCount 32`, z -16..15 (`art/catalogue/geometry.json:4-9`). So a "depth 1" or "1 ft" state has no single stratum it maps to. The registry text itself has no 9-layer statement; the 5-level statement is in the natural-systems doc.
- **D5. System names.** Nine rows use `CREATURE_ECOLOGY` (registry:153-161), which is not in the §2 enum (registry:52-66). The enum has `ECOLOGY_WILDLIFE`, which no row uses. These are the 9 WSR-01 findings.
