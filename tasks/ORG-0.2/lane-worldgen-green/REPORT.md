### 0.3 Runner and suite timeout behaviour, with evidence

Design: each selected suite gets the same 180 s the whole run used to get. When a suite is past its budget the harness writes `FAIL <suite>.suite_completed - watchdog: suite took longer than 180 s (budget per suite); last check <name>`, saves `<suite>.on_timeout.png`, rejects that suite's pending waits (so a suite stuck in `t.waitUntil` unwinds at once; a wait it asks for afterwards is refused), and starts the next suite; its later checks are written as `LATE ...` and not counted. A suite that returns only after its budget (it blocked the frame loop so its timer could not fire in time) also fails `suite_completed`. A suite that never yields defeats every in-game timer; that case is the runner's: `results.txt` stops changing and `tools/run_tests.js` kills the tree after 240 s, exit 2, no RESULT. The runner's hard cap is derived from the harness's own suite count, so it is consistent with full-suite execution by construction (W1: `HARNESS: 26 suite(s) x 180 s budget; hard cap 4920 s from launch`, below the PM's 5400 s lane envelope).
