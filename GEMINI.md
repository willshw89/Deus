## Your role (set by the user 2026-09-18): art
- **MANDATORY: ALL GENERATION TASKS ARE TO UTILIZE GOOGLE NANO BANANA II.** (User decisions 2026-09-19; AGENTS.md Rule 11; VISION V69, V70, V79, V109.) Every visual asset across all categories (characters, creatures, wildlife, monsters, terrain, autotiles, world objects, items, equipment layers, portraits, facesets, icons, and UI) MUST originate exclusively from Google Nano Banana II (`generate_image`). No other generator model is allowed, and no agent is permitted to type in sprites pixel-by-pixel in code. Everything begins with an authentic Nano Banana II generation, processed into standard RMMZ formats via palette snapping to `art/palette/uf.hex` and clean-up tooling.
- **MANDATORY: ALL ANIMATION MUST HAPPEN THROUGH THE SPRITE. NO AFTER-EFFECT ANIMATIONS.** (User decisions 2026-09-19; AGENTS.md Rule 12; VISION V60, V108.) All animations across every entity and environmental asset—humanoids, wildlife, monsters, trees, flora, crops, fire, water, doors, workshops, and world objects—must be delivered as actual, distinct pixel sprite animation frames on the sprite sheets (e.g. 4-direction action cycles, multi-frame wind sway, flickering flame loops, rippling water waves). No animation is to be faked or produced using code-driven after-effects, procedural scaling/squashing, sine-wave swaying, rotation, or shader distortions. Every motion comes directly from the sprite frames.
- **STANDARDIZED 4-DIRECTION ANIMATIONS FOR 8-DIRECTION MOVEMENT:** (User decisions 2026-09-19; VISION V110.) Movement in the engine remains 8 directions, but all animation charsets are standardized on 4 facings (South, West, East, North) with East mirrored from West where symmetrical. This eliminates production bottlenecks while preserving responsive navigation.
- **ZERO FLYING PROJECTILES ON SPRITE SHEETS; SPELL INITIATION ONLY:** (User decisions 2026-09-19; VISION V111.) Bow attack frames are string draw/tension/pluck recoil ONLY (zero flying arrows; projectile arrows are animated separately by engine/system). Magic attack frames are spell initiation chant/incantation postures with soft palm or staff aura ONLY (zero flying projectile beams, bursts, or leaves).
- **ONE CREATURE / DEMOGRAPHIC AT A TIME WITH INVARIANT UNIFORM SCALE:** (User decisions 2026-09-19; VISION V112.) Generate and perfect characters one demographic at a time (e.g., Adult Male Elf first, then Adult Female Elf, then Elf Child). Every action pose within a demographic must share the exact same invariant global scale factor (e.g. 40.0/276.0 for adult male elf) anchored to the native baseline y=47, preventing bounding-box scaling distortion.
- **DEDICATED HAULING / CARRYING POSE:** (User decisions 2026-09-19; AR-600 column 7.) Dedicated pose holding heavy load (crate, timber, stone, burlap sack) in front of chest in both arms.
- Make the assets listed in **`docs/ASSET_REQUESTS.md`**, exactly to spec. That file is your work queue. Each engine feature comes with a **handoff report in `docs/handoffs/`** explaining what to make and how to plug it in. World objects go into `game/data/UF_WorldCatalog.json`, which is the one data file you may edit (`HANDOFF_world_generation.md`). Update each request's status as you go (`IN PROGRESS`, `DELIVERED`).
- **The look is HD pixel art in the style of Final Fantasy VI** (user decisions 2026-09-19; VISION V2, V44): flat 3/4 top-down RPG view, upright sprites, no lean, sized against the 48 px RPG Maker grid square, 16-bit palette (`art/palette/uf.hex`). Follow `docs/ART_STANDARD.md` and `docs/RMMZ_ASSET_SPEC.md`. `docs/GUIDE_25D.md` and everything about the Ultima VII lean are **obsolete**: don't make 2.5D art, don't extract Ultima VII shapes any more.
- **Placeholders are RPG Maker's stock art** (the `Outside_*` tiles, `People`/`Actor`/`Nature`/`Monster` sheets). Your job is the originals that replace them, request by request in `docs/ASSET_REQUESTS.md`, in the FF6 manner, on the layered sheet standard (AR-600) when it applies. Existing `U7_` files are not to be extended; they get replaced.
- **Interaction states:** every asset is designed with the states the engine uses (standing/stump, full/picked, unlit/lit, intact/ruined, alive/dead, clothing tiers, age stages). `docs/ASSET_INVENTORY.md` lists them per asset.

## How to find what needs art
1. **Run the inventory tool** from the project folder: `"C:\Program Files\nodejs\node.exe" tools\generate_asset_inventory.js`. It rewrites `docs/ASSET_INVENTORY.md` and `game/data/UF_AssetIndex.json` from the catalog, the plugins, `game/img`, `docs/STATUS.md` and `docs/ASSET_REQUESTS.md`, and prints PASS/FAIL lines (a FAIL names a real problem, such as a referenced file that doesn't exist). Claude Code owns the tool; you run it. Never edit the two files it writes.
2. **Read `docs/ASSET_INVENTORY.md`**: the summary counts by status, then one table per category (ground and water tiles, objects, items, creatures, people, UI and system, generated placeholders). Every row gives the key/file the engine uses, what uses it, **the interaction states the art needs**, the status (`missing`, `stock RMMZ`, `U7 stand-in`, `generated`, `original`) and the request row with its status word. Your queue is the rows whose request is open (REQUESTED, IN PROGRESS, PARTLY DELIVERED, BACK TO IN PROGRESS); every `stock RMMZ` and `U7 stand-in` row needs an original eventually.
3. **"Needs a request"** lists assets with no `AR-` row. Don't invent an ID or add a row: write it under "Notes for Claude Code" in `docs/ASSET_REQUESTS.md` and Claude Code adds the request with a spec.
4. **Hover things in Playtest** (F5 in the RMMZ editor): the look tooltip next to the cursor ends with the art line `<file> — <status> (<request id>)` (`UF_Look`, reading `UF_AssetIndex.json`), so you can find the file behind anything you see on screen.
5. **Look at the test screenshots** in `game/test_output/` (or a test snapshot's `test_output/` under `%TEMP%\uf_snapshots\<name>\`): the start at three zoom levels, a far corner of the map, herds, sites, the look tooltip. Anything that looks wrong there is worth a note.
6. **Design every asset with its listed states** before drawing: standing/stump, full/picked (and regrown), unbuilt/built/ruined, unlit/lit, alive/dead, the clothing tiers and held tools, the 4 facings and the animation columns of AR-600. One state = one frame, column or file, as `docs/ART_STANDARD.md` and the request say. A state the engine can't switch to is wasted; one it needs and lacks shows up as a tint of the wrong image.
7. **When you deliver**, put the exact file name, backticked, in the request's Status column (for example ``DELIVERED (`!$Oak.png`, `!$Oak_stump.png`)``): that is how the tool links the file to the request. Then run the tool again and check that the row's request and status changed.
8. **The brief for every asset** is in `docs/asset_briefs/` (one segment file per family; start with `docs/asset_briefs/INDEX.md`: segments, working order, delivery procedure). The brief is the spec; the request row is the queue and status.
